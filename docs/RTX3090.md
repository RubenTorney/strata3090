# Strata sur une RTX 3090 : paramétrage optimal et mode vision

Tout ce qui suit a été mesuré les 11 et 12 octobre 2026 sur un seul PC : RTX 3090 24 Go (PCIe 4.0 x16, la carte
affiche aussi le bureau), Ryzen 5 5600X (6 cœurs, AVX2), 62 Gio de DDR4, Ubuntu 24.04, noyau 7.0, pilote NVIDIA
595.99.02, CUDA 13.2. Modèle : Qwen3.8-Flash-Next GSQ-RCO IQ3_S, contexte 262 144, K/V int8, brouillon MTP, vocabulaire
de brouillon `fr`. Moteur : la branche `opt/3090` (amont v0.1.43 + le tier adaptatif asynchrone + les options
ci-dessous). Les fichiers de mesure sont dans `bench/results/2026-10-12-rtx3090-max/` et `bench/vision/`.

## Résultat

| Configuration | Débit de génération (tok/s) |
| --- | ---: |
| Installation d'origine (v0.1.42, réglages de setup) | 94,5 |
| + réglages calibrés et `--adapt-async 1` (v0.1.42) | 117,3 |
| Base de cette branche (v0.1.43, mêmes réglages, options désactivées) | 117,0 |
| + PCIe en parallèle, copie 64 blocs, noyau « up » rapide | 119,5 |
| + noyau CPU Zen 3 | 120,5 |
| + `--adapt-swaps 160` (configuration retenue) | 122,2 à 123,7 |

Médiane sur 12 prompts à froid (6 en français, 6 en anglais ; texte, code, SQL), 256 tokens générés chacun, un moteur
neuf par mesure, 2 requêtes d'échauffement. Les lignes 3 à 5 sont la médiane de trois passes alternées (écart entre
passes : 0,3 tok/s au plus) ; la dernière ligne regroupe cinq mesures d'une passe faites dans cinq séries
(122,2, 122,7, 122,5, 123,7 et 122,2). Les
deux premières lignes viennent du protocole de la veille (température 0,7), les autres du pilote
`tools/strata_ab_linux.py` (température 0) : les deux protocoles donnent 117 pour la même configuration.

Gain de cette branche sur sa base : environ +4,5 %. Gain total depuis l'installation d'origine : environ +30 %, dont
l'essentiel vient des réglages et du tier asynchrone, pas du nouveau code.

## La configuration retenue

Dans `strata-iq3_s.json` (copie : `bench/results/2026-10-12-rtx3090-max/config_rtx3090_max.json`) :

```
--max-context 262144 --kv int8 --kv-grow --spec 4 --spec-min-p 0.70
--pcie-frac 0.35 --adapt-every 1 --adapt-swaps 160 --adapt-decay 0.97 --adapt-async 1
--vision --vram-reserve-mib 700
"env": { "STRATA_PCIE_BRANCH": "1", "STRATA_FETCH_BLOCKS": "64", "STRATA_GR_FAST": "1", "STRATA_IQ_ZEN3": "1" }
```

| Réglage | Ce qu'il fait | Mesure |
| --- | --- | --- |
| `--adapt-async 1` | le cache d'experts en VRAM s'adapte sans bloquer la génération | +14 % (v0.1.42 : 102,9 → 117,3) |
| `--kv-grow` | la mémoire de conversation grandit à la demande au lieu d'être réservée pour 262K | +6 % (94,5 → 100,0, v0.1.42) |
| `--adapt-every 1 --adapt-swaps 160 --adapt-decay 0.97` | le cache est réévalué à chaque fenêtre, jusqu'à 160 échanges | 160 contre 80 : +1,6 % (deux fois) |
| `--pcie-frac 0.35` | 35 % des experts absents du cache sont lus par le GPU en RAM, le reste est calculé sur le CPU | 0,25 : −2,4 % ; 0,45 : dans le bruit |
| `--spec 4 --spec-min-p 0.70` | fenêtre de 4 tokens, un brouillon entre s'il a au moins 70 % de probabilité | 0,60 : −0,5 % ; 0,80 : −2,5 % |
| `STRATA_PCIE_BRANCH=1 STRATA_FETCH_BLOCKS=64` | la part PCIe d'une couche tourne à côté des experts en VRAM ; copie sur 64 blocs larges | +0,9 % à travail égal (4 prompts sur 4) |
| `STRATA_GR_FAST=1` | noyau « up » de la lecture hyper-connexion sans chaîne de latence (il existait déjà dans le code) | +1,5 % à travail égal (3 sur 3) |
| `STRATA_IQ_ZEN3=1` | décodage AVX2 sans gather pour IQ2_S et IQ3_S, noyau multi-token aussi pour un token seul | +0,8 % (119,5 → 120,5) |

Les trois dernières lignes ensemble : +3,0 % en configuration réelle (117,0 → 120,5).

`STRATA_IQ_ZEN3=1` change l'arrondi d'un token seul : les réponses ne sont plus identiques bit pour bit à celles du
chemin par défaut. Les trois autres variables donnent les mêmes valeurs par construction ; la lecture hyper-connexion
est en plus vérifiée bit pour bit par le moteur à chaque démarrage. La parité de bout en bout n'a pas pu être montrée
par comparaison de texte (voir « Ce qui reste ouvert »).

## Contexte long et réponses longues

Configuration retenue, un seul moteur, quatre prompts de plus en plus longs tirés du dépôt (documentation puis code
source) suivis d'une question, 256 tokens générés. Le préfixe commun est réutilisé d'une requête à la suivante.

| Jetons du prompt | dont relus | Lecture (tok/s) | Génération `int8` (tok/s) | Génération `k8v4` (tok/s) | Experts en cache (`int8`) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 30 105 | 30 105 | 2 476 | 101,6 / 101,8 / 101,1 | 102,9 / 103,0 / 102,9 | 8 545 |
| 98 610 | 82 226 | 2 385 | 107,8 / 108,5 / 106,8 | 106,1 / 106,3 / 105,4 | 8 057 |
| 195 234 | 96 930 | 2 174 | 104,3 / 90,4 / 91,8 | 94,8 / 96,5 / 95,4 | 7 437 |
| 213 135 | 32 911 | 1 969 | 92,1 / 97,0 / 94,0 | 98,2 / 100,2 / 93,5 | 7 275 |
| 246 041 | 33 049 | 1 870 | 93,1 / 93,9 | 93,2 / 95,2 | 7 057 |

Trois passes (deux pour la dernière ligne), un moteur neuf par passe. À 246K jetons de contexte, tout près de la limite
de 262 144, la génération tient environ 93,5 tok/s, soit 24 % de moins qu'à contexte court sur des prompts différents.
La mémoire de conversation prend alors 3,25 Gio et le cache a rendu 1 594 emplacements d'experts pour elle.

`--kv k8v4` (mémoire plus compacte : 2,57 Gio au lieu de 3,25 à 254K cellules, 363 experts de plus en cache) ne se
distingue pas d'`int8` en génération (écarts de 0 à 3 %, dans le bruit entre passes) et lit le prompt 7 % moins vite :
`int8` est gardé.

Une réponse de 2 500 tokens d'affilée (exposé avec exemples de code) sort à 124,8 tok/s.

## Parité des options « mêmes valeurs »

Sous `STRATA_DETERMINISTIC=1 --adapt-swaps 0`, cache et prefill fixés, six configurations ont donné exactement le même
texte sur 12 prompts sur 12 (256 tokens) : la base, `STRATA_PCIE_BRANCH=1 STRATA_FETCH_BLOCKS=64`, `STRATA_GR_FAST=1`,
les deux ensemble, `STRATA_GR_SM86=1` et `STRATA_GR_ACT_AHEAD=1` (seconde passe de `speed2_det.jsonl`). Trois moteurs
relancés plus tard redonnent ce texte, et quatre autres concordent à 128 tokens (`det_bisect.txt`).

## Mode déterministe : la cause de la variation restante

Dans la série `speed2_det`, les réponses formaient trois groupes de moteurs consécutifs. Leurs journaux montrent trois
tailles de cache : 8 687, 8 688 et 8 703 emplacements, pour un même `--expert-cache 8400`. Un cache demandé près de ce
qui tient en VRAM est réduit par le moteur d'après la VRAM libre au démarrage, et celle-ci varie de quelques Mio avec
le bureau. Un expert de plus ou de moins en cache change la répartition entre GPU et CPU, donc les arrondis.

Avec un cache demandé nettement plus petit (`--cache-slots 5200`, K/V élastique désactivé), six moteurs lancés sous
trois réserves de VRAM différentes (700, 900 et 1 100 Mio) ont ouvert le même cache (6 793 emplacements) et donné les
mêmes réponses sur 12 prompts sur 12 (`det_nogrow.txt`). À `--cache-slots 6300`, les trois réserves donnaient trois
tailles (7 068, 6 964, 6 860) et trois jeux de réponses.

Le pilote désactive maintenant le K/V élastique en mode déterministe et avertit quand les moteurs d'une série n'ont
pas ouvert le même cache ; le moteur avertit si `--kv-grow` est actif sous `STRATA_DETERMINISTIC=1`. Avec le tier
adaptatif actif (la configuration réelle), le texte varie toujours d'un lancement à l'autre : c'est voulu, le tier
suit le temps réel.

## Où part le temps

Une fenêtre de vérification dure environ 26 ms et valide 3,3 tokens. Le moteur passe 13,9 ms à attendre le GPU, 9,5 ms
dans les experts calculés sur le CPU et 1,6 ms dans le brouillon (profil de la v0.1.43, `--adapt-async 1`). Le cache
garde environ 8 440 experts en VRAM (16 Gio) et sert 91 à 94 % des appels ; chaque expert absent coûte un calcul CPU
d'environ 0,2 à 0,35 ms sur un thread ou une lecture PCIe.

Un profil `perf` du moteur pendant une réponse de 2 500 tokens (`cpu_profile_decode.txt`) : 63 % des échantillons CPU
sont dans la boucle d'attente des six threads de calcul, 10 % dans l'attente du thread hôte sur les drapeaux du GPU, et
environ 23 % dans les noyaux d'experts. Les threads sont donc inoccupés les deux tiers du temps.

Le détail par couche (`bench/results/2026-10-12-rtx3090-latency/`, `STRATA_DECODE_TIMING=1 STRATA_POOL_STAMPS=1`, un
prompt, 109 fenêtres de 20,8 ms) montre que cette inactivité est le temps pendant lequel le GPU travaille, pas une
perte dans la répartition du travail :

| Par couche, côté hôte | Temps |
| --- | ---: |
| plan GPU, quantification des activations, préparation des tâches | 5 µs |
| lignes gate/up des experts absents (6 threads, 18 tranches) | 100 µs |
| lignes down | 48 µs |
| synchronisation entre threads (les deux phases) | 0,8 µs |
| total | environ 155 µs, dont 148 de calcul |

Un expert absent coûte environ 80 µs de calcul sur six threads, au débit du décodage des poids quantifiés (4,3 Go/s par
thread). Côté GPU, l'attente visible des experts absents est de 4,5 ms par fenêtre (1,8 pour les lignes CPU, 2,7 pour
la part PCIe) ; le reste, 13 à 14 ms, est le temps des noyaux GPU eux-mêmes. Supprimer un saut de réveil, découper plus
fin ou fusionner les deux phases rapporterait au plus 0,2 à 0,4 % : rien de cela n'a été codé. `--pool-tasks 12` et
`36` mesurent 122,8 contre 122,8.

Ce qui borne le débit sur cette machine, dans l'ordre : le temps des noyaux GPU (lecture des poids en VRAM, à chaque
fenêtre), le nombre de tokens validés par fenêtre (il dépend du modèle de brouillon) et le nombre d'experts absents du
cache (il dépend de la VRAM libre). Aucun des trois ne se règle par un paramètre : une cinquantaine de réglages et
d'interrupteurs ont été mesurés (CPU, cache, graphe GPU), et les quatre retenus donnent ensemble +4,5 %. Au-delà, le gain passe par le matériel
(plus de VRAM ou une seconde carte pour le cache, un CPU plus rapide pour les experts absents).

## Mode vision

Le modèle a un encodeur d'images (0,9 Go) que l'installation ajoute avec `--vision cpu` ou `--vision gpu`. Ici il tourne
sur le CPU (6 threads) : il ne prend pas de VRAM, et le cache d'experts garde la même taille (8 439 experts avec la
vision, 8 441 sans). Les 700 Mio de `--vram-reserve-mib` que l'installation écrit avec la vision sont la réserve par
défaut du moteur, pas un surcoût.

### Benchmark : une capture d'écran refaite en un fichier HTML

`bench/vision/vision_bench.py` envoie une capture 1280 × 900 de la page d'accueil de Hacker News avec la demande de la
refaire en un seul fichier HTML autonome, réflexion désactivée, température 0. Il garde la réponse, le HTML, un rendu
du HTML par Firefox et les temps dans `stats.jsonl`.

| Jetons d'image au plus | Jetons du prompt | Encodage (CPU) | Tokens générés | Débit | Brouillons acceptés | Durée totale |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 300 (défaut du mode CPU) | 376 | 2,7 s | 4 593 | 148,9 tok/s | 93,5 % | 34,5 s |
| 1 024 | 1 084 | 13,3 s | 5 284 | 147,6 tok/s | 93,7 % | 50,8 s |

Les deux réponses sont des pages HTML complètes qui s'affichent.

- À 300 jetons, la mise en page, le bandeau et la plupart des titres sont justes, mais le petit texte est inventé :
  domaines, auteurs et compteurs sont faux, et un titre est remplacé (« IRCv3 » devient « RICO (1970) »).
- À 1 024 jetons, le texte est presque entièrement exact, petits caractères compris, avec quelques fautes de lettres
  (« jtnr » pour « jttnr », « apswo » pour « apsw »). La page rendue est un peu plus étroite que l'original.

Pour refaire une page à partir d'une capture, il faut donc 1 024 jetons d'image : la configuration retenue met
`"max_tokens": 1024` dans la section `vision`. Le coût est d'environ 10 s d'encodage de plus par nouvelle image ; une
image déjà envoyée n'est pas encodée de nouveau. Pour décrire une photo, 300 suffit et répond plus vite.

Le débit monte à 148 tok/s sur ce test parce que le HTML est répétitif : 93 % des brouillons sont acceptés, contre 70 à
80 % sur du texte courant.

Refaire le test :

```
python bench/vision/vision_bench.py CONFIG.json bench/vision/site_hn.png bench/vision/run2 --tag hn --image-tokens 300,1024
```

Le serveur en service doit être arrêté d'abord : deux moteurs ne tiennent pas dans 62 Gio de RAM.

## Mesurer soi-même

`tools/strata_ab_linux.py` compare des moteurs ou des réglages : un moteur neuf par bras, 12 prompts, port 18080.

```
export STRATA_DIR=~/Documents/strata STRATA_AB_CONFIG=~/Documents/strata/strata-iq3_s.json
python tools/strata_ab_linux.py speed --no-deterministic --rounds 3 --max-tokens 256 \
    --arm 'base' --arm 'essai;env=STRATA_X=1;arg=--flag valeur'
```

Avec `--no-deterministic`, les textes changent d'un lancement à l'autre et seules les médianes par passe se comparent ;
elles se reproduisent ici à 0,3 tok/s près. Sans cette option, le pilote active `STRATA_DETERMINISTIC=1` et compare les
prompts dont le texte est identique.

## Ce qui reste ouvert

- **Le tier bloquant de la v0.1.43** mesure 83,4 tok/s ici contre 102,7 en v0.1.42 ; la cause n'est pas isolée. La
  configuration retenue utilise le tier asynchrone et n'est pas touchée.
- **Longues sessions.** Le contexte long est mesuré jusqu'à 246K jetons sur des prompts lus d'un bloc ; une conversation
  réelle de plusieurs heures, avec beaucoup de tours, ne l'est pas.
- **Coût des pauses entre noyaux GPU.** `STRATA_DUMMY_NODES=200` a échoué au démarrage (HTTP 400) : ce coût n'est pas
  chiffré.
- **Backends.** Seul le build CUDA sm_86 sous Linux a été compilé et lancé ; ni HIP, ni SYCL, ni Windows.
- **Outils de profil** (`tools/profile_personal.py`, `tools/vram_budget.py`) : ils fonctionnent, mais le profil n'a pas
  apporté de débit ici.
